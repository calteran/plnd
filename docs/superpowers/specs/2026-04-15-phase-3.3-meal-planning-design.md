# Phase 3.3: Meal Planning — Design Spec

**Date**: 2026-04-15
**Status**: Draft
**Related**: [Phase 3 AI design](./2026-04-01-phase3-ai-design.md), [Meals step redesign](./2026-03-27-meals-step-redesign-design.md)

---

## Context

Phase 3.2 shipped intent-driven task entry backed by the `plnd_agent` crate. Phase 3.3 extends agentic capabilities into meal planning — PLND's most differentiating domain for neurodivergent users, where picky eating, decision fatigue, and nutritional drift are central problems.

The weekly planning wizard already has a Meals step that populates cells from a mock `MealSuggestionsService`. The day view renders meals but exposes no meaningful per-meal interactions beyond a `Plan ›` stub and a done chip. Phase 3.3 replaces the mock suggestions with real LLM-powered proposals, introduces approval / rebalance / swap interactions across both surfaces, and adds nutrition visibility.

All terminology in user-facing copy uses **meal** — "slot" is an implementation-only concept.

---

## Scope

In scope:

- Full-week generation inside the wizard's Meals step (replaces the mock suggestions service).
- Per-meal approval, refresh, edit, and skip interactions in the wizard.
- Top-level rebalance of unapproved meals with an explicit confirmation.
- Day-view per-meal Review pane with nutrition, dishes, prep notes, and swap/edit/skip/done actions.
- Done-checkbox on meal rows so the happy path requires no panel open.
- Shared text-resolution path (`description → meal_ref`) reused by both surfaces, including best-effort nutrition estimation for meals not found in the catalog.

Out of scope (deferred to later phases):

- Grocery list generation (Phase 4).
- Exercise AI.
- Recurring meal templates beyond existing behaviour.
- Strict allergen enforcement beyond `UserIngredientPref` blocking already in place.

## User-facing design

### Weekly planning wizard — Meals step

**Cell state machine:** `proposed` → `approved` | `skipped`. No free-standing "custom" state; custom text resolves into `approved` with a custom meal reference.

**Cell actions**

| Action | Icon | Behaviour |
|---|---|---|
| Refresh | 🔀 | Single-slot agent call. Returns one meal; cell auto-approves with the new reference. |
| Edit    | ✏️ | Opens text input; on submit, calls the resolver. Result auto-approves the cell. |
| Approve | ✓ | Freezes current proposal as-is. |
| Skip    | × | Marks the meal as intentionally blank. |

**Step entry**

- On first entry for a given week: auto-POST `/agent/meal-plan`. All cells render as `proposed`.
- On return entry (wizard already populated): reuse stored grid; do not re-generate.
- Loading state: skeleton grid with shimmer; cancel button aborts the in-flight request.

**Top-level Refresh**

Button above the grid. On click, show a modal:

> "This will replace **N** unapproved meals. Approved and edited meals stay as they are. Continue?"

Confirm → POST `/agent/meal-plan/rebalance`. Only unapproved cells are sent as open; approved / custom / skipped come back untouched.

**Next button**

All remaining `proposed` cells commit as-is (same wholesale commit via `WeekPlanService.commitPlan()` that the wizard uses today).

**Approval is client-local state.** No DB column, no `schedule_entries.status` change. The full plan commits at the end of the wizard.

### Day view

**Row anatomy (today's `MealRowComponent`):**

- Emoji, meal name, optional subtitle (from description).
- **Done checkbox** — one click toggles completion without opening the panel.
- **Review** button — expands inline pane (no side drawer).

**Review pane contents**

- **Filled, catalog meal:** name, occasion, servings, nutrition (kcal, protein, carbs, fat), dish list, prep notes.
- **Filled, custom meal:** same layout with `~` prefix on nutrition values, dashed border on the nutrition chip, and an "Estimated from similar catalog meals. Edit to refine." footnote.
- **Empty slot:** "No meal scheduled" heading and empty-state actions.

**Pane actions**

| Filled | Empty |
|---|---|
| 🔀 Swap · ✏️ Edit · × Skip · Mark done | ➕ Add meal · 🔀 Suggest one · × Skip |

Swap / Add / Edit open an inline text field driven by the shared resolver. "Suggest one" on an empty slot fires `/agent/meal-plan/suggest-slot` directly — no text input.

## Backend — `plnd_agent`

### New tools (`plnd_agent/src/tools/meal.rs`)

| Tool | Terminal | Purpose |
|---|---|---|
| `get_user_meal_preferences` | no | Dietary restrictions, top-rated meals, blocked ingredients, allergens. |
| `search_meal_catalog` | no | Wraps `ProviderSearchService::search_meals`. Accepts query + occasion + filters. |
| `get_user_meal_library` | no | FTS over `user_meals` for this user. |
| `get_meal_nutrition` | no | Computed macros for a known meal reference (`{type: "catalog" \| "user", id}`). |
| `estimate_nutrition_from_description` | no | Given a custom meal name and inferred ingredient list, look each ingredient up via `ProviderSearchService` (USDA FDC primary, Open Food Facts fallback) and aggregate. Returns estimated macros + `estimated: true`. |
| `get_week_schedule` | no | Returns the 7-day meal state that Angular POSTed with the request (approved / skipped / custom meals the agent must preserve). The request payload, not the DB, is the source of truth for unapproved-meal context. |
| `propose_meal_plan(slots)` | **yes** | Full-week plan. |
| `rebalance_meal_plan(slots)` | **yes** | Post-pin rebalance respecting approved / skipped / custom. |
| `suggest_slot_meal(date, occasion)` | **yes** | Cheap single-meal suggestion; does not consider whole-week nutrition balance. |
| `resolve_meal_description(text, occasion, date)` | **yes** | Free text → `meal_ref` (catalog, user, or new custom) + optional estimated nutrition. |

Memory tools (`save_memory`, `update_memory`, `forget_memory`, `get_user_memories`) already exist from Phase 3.1 and are registered for these use cases with categories `food` and `habits`.

### New use cases (`plnd_agent/src/context/mod.rs`)

```rust
pub enum UseCase {
    TaskEntry,
    MealPlanning,       // full-week generate — Capable tier
    MealRebalance,      // post-pin rebalance — Capable tier
    MealSuggestSlot,    // single meal suggestion — Capable tier (revisit for Fast later)
    MealAdhocResolve,   // free text → meal_ref — Capable tier (revisit for Fast later)
}
```

Each use case filters its memory injection to `food` + `habits`, binds a tool subset, and wires a JSON-schema response validator.

### Prompts (`plnd_agent/src/prompts/`)

- `meal_planning.md` — exists, revise to reference the updated tool set.
- `meal_rebalance.md` — exists, revise likewise.
- `meal_suggest_slot.md` — new. One-shot, cheap single-meal suggestion with preferences but no whole-week reasoning.
- `meal_adhoc_resolve.md` — new. Free text → match library/catalog → fall back to drafting a custom meal with nutrition estimation.

### Response schemas (`plnd_agent/src/schemas/`)

Four new JSON Schema Draft 7 validators (compiled once in `LazyLock`, following the `TASK_ENTRY_RESPONSE_SCHEMA` pattern):

- `MEAL_PLAN_RESPONSE_SCHEMA` — `{ week: date, meals: MealSlot[], nutrition_summary: {...} }`
- `REBALANCE_RESPONSE_SCHEMA` — same as above
- `SUGGEST_SLOT_RESPONSE_SCHEMA` — `{ date, occasion, meal_ref: { type, id, estimated_nutrition? } }`
- `RESOLVE_RESPONSE_SCHEMA` — `{ meal_ref: { type, id }, estimated_nutrition?, confirmation }`

`MealSlot` payload:

```json
{
  "date": "2026-04-16",
  "occasion": "breakfast",
  "meal_ref": { "type": "catalog", "id": "..." },
  "estimated_nutrition": {
    "kcal": 340,
    "protein_g": 14,
    "carbs_g": 55,
    "fat_g": 8
  }
}
```

`estimated_nutrition` is populated only when `meal_ref.type == "user"` and `nutrition_estimated` is true. The agent never emits an approval state — approval is strictly client-side.

## Backend — `plnd_api`

New routes under the existing `/agent` nest:

| Method | Path | Use case |
|---|---|---|
| POST | `/agent/meal-plan` | `MealPlanning` |
| POST | `/agent/meal-plan/rebalance` | `MealRebalance` |
| POST | `/agent/meal-plan/suggest` | `MealSuggestSlot` |
| POST | `/agent/meal-plan/resolve` | `MealAdhocResolve` |

All four:

- Require auth (`user_id` from session — never from payload).
- Use the existing `agent_task_limiter` rate limiter.
- Validate the LLM response against the use-case schema before returning.
- Return a structured JSON envelope (never raw LLM text).

The placeholder handler at `/agent/meal-plan` (currently returning 501) is replaced.

### Migration

```sql
ALTER TABLE user_meals
    ADD COLUMN nutrition_estimated BOOLEAN NOT NULL DEFAULT FALSE;
```

Existing rows default `false` (nutrition was either manually entered or derived from linked catalog dishes).

- `UserMealStore::create_from_description(user_id, name, occasion_tags, dishes_opt, nutrition, estimated: bool) -> UserMeal` — insert path for the resolver when no catalog match exists.
- `ScheduleStore::get_week_meals(user_id, start_date) -> Vec<WeekMealSlot>` — read-side query consumed by `get_week_schedule` tool.

No other domain changes.

## Security

No new attack surfaces beyond Phase 3 baseline.

- `user_id` always sourced from auth session; never included in tool inputs.
- All user text (wizard text entry, day-view swap input) wrapped in `<user_input>` delimiters before injection into prompts.
- Indirectly-sourced data (catalog search results, memory content) wrapped in `<data>` delimiters.
- All four meal responses validated against their JSON schema before returning — raw LLM output never reaches Angular.
- Rate limiting applied per route via `agent_task_limiter`.

## Rollout

Nine vertical slices, each its own sub-issue and PR, mergeable independently. Order preserves at-main stability: tools first, then routes, then UI.

1. `user_meals.nutrition_estimated` migration + `UserMealStore::create_from_description`.
2. Read-side tools: `search_meal_catalog`, `get_user_meal_library`, `get_user_meal_preferences`.
3. `estimate_nutrition_from_description` + `get_meal_nutrition`.
4. `MealPlanning` use case: `get_week_schedule` + `propose_meal_plan` + revised `meal_planning.md` + schema + `/agent/meal-plan` wired end-to-end.
5. `MealRebalance`: `rebalance_meal_plan` + revised prompt + schema + route.
6. `MealSuggestSlot`: `suggest_slot_meal` + new prompt + schema + route.
7. `MealAdhocResolve`: `resolve_meal_description` + new prompt + schema + route.
8. Angular wizard: auto-generate, approval state, ✓/🔀/✏️/× actions, top-level Refresh + confirmation, retire `MealSuggestionsService`.
9. Angular day view: done checkbox, Review button, `MealReviewPaneComponent`, swap/add text input wired to resolver.

A separate PLANNING.md touch-up PR merges alongside slice 1 to keep the roadmap in sync.
