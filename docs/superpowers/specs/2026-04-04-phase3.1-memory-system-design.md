# Phase 3.1 — Memory System Design

**Date**: 2026-04-04
**Status**: Approved
**Builds on**: Phase 3.0 (plnd_agent foundation — calteran/plnd#225)
**Required by**: Phase 3.2 (Task Entry), Phase 3.3 (Meal Planning Wizard)

## Overview

Phase 3.1 introduces a persistent user memory system. The agent accumulates contextual
observations about the user over time (energy patterns, food preferences, schedule habits),
stores them in a `user_memories` table, and injects a filtered subset into the system
context at the start of each agent run. The LLM manages its own memory lifecycle via four
registered tools.

## Architecture

### Database (`plnd_data`)

New table `user_memories`:

```sql
CREATE TABLE user_memories (
    memory_id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    category    VARCHAR(50) NOT NULL CHECK (category IN ('food', 'schedule', 'energy', 'habits', 'general')),
    content     TEXT NOT NULL,
    tags        TEXT[] NOT NULL DEFAULT '{}',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_user_memories_user_category ON user_memories(user_id, category);
```

### Memory Categories

| Category   | Examples                                              | Used in                |
|------------|-------------------------------------------------------|------------------------|
| `food`     | "always has the same breakfast"                       | Meal planning          |
| `schedule` | "productive in the mornings"                          | Task entry             |
| `energy`   | "low energy on Mondays"                               | Task entry             |
| `habits`   | "Fridays = sandwich", "vacuum filter replaced monthly" | Task entry + Meal planning |
| `general`  | anything else                                         | Available via tool retrieval only; not auto-injected |

### Context Injection (`AgentService::run`)

At the start of each run, load memories filtered by `UseCase`:

- **Task entry**: `habits` + `schedule` + `energy`
- **Meal planning**: `food` + `habits`

Inject as an XML block before user input:

```xml
<memory>
  <entry category="schedule">productive in the mornings</entry>
  <entry category="habits">Fridays = sandwich</entry>
</memory>
```

If no memories exist for the use case, omit the block entirely.

### Memory Tools (`plnd_agent/src/tools/`)

Four tools registered in `ToolRegistry`, available to both use cases:

| Tool | Signature | Notes |
|------|-----------|-------|
| `get_user_memories` | `(category: Option<String>) -> Vec<UserMemory>` | Mid-loop retrieval |
| `save_memory` | `(category, content, tags)` | Rate-limited |
| `update_memory` | `(memory_id, content)` | Rate-limited |
| `forget_memory` | `(memory_id)` | Rate-limited |

**Security**: `user_id` is always sourced from `ToolContext` (authenticated session), never
from LLM-generated output. Write operations are rate-limited to prevent abuse.

## Dependency Order

```
#A  DB migration (user_memories table)
  └── #B  Memory CRUD in plnd_data
        ├── #C  Memory injection into agent context (by UseCase)
        └── #D  Memory tools (get, save, update, forget)  ← parallel with C
```

## Verification

- `just verify-build` passes
- `just test-ci` passes including memory tool unit tests
- `AgentService::run()` injects filtered memories for both use cases
- Memory write tools are rate-limited; `user_id` from `ToolContext` only
- All memories injected into prompts are wrapped in `<memory>` XML delimiters
- Empty memory set → no `<memory>` block injected
